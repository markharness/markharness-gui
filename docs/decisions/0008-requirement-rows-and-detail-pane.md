# 0008: 第1版の表示は、要求ごとの行と詳細ペインで構成する

## ステータス

Accepted(2026-10-05決定)。第1版の最小の形である。親子の集計、件数の扱い、折り畳み、強調と優先づけ、視点の切り替え、読む文脈の選択は、第1版に含めない([0009](0009-fact-provenance-and-human-attention.md))。StrictDocの親子は、関係そのものだけを示す。

## 背景

このGUIの目的は、Knowledgeの関係を可視化することではなく、人間が、短時間で、どの要求のVerificationに注意が必要か、その理由は何かを判断できるようにすることである。

Release Coverageで、人間が判断する単位は、要求である。「この要求は、十分にテストされているか」を、要求の文と、そのケースの題名を、並べて読んで判断する。そのため、判断に要るもの(要求の文、ケースの題名)は、要求の行に出ているべきである。

先行モックアップ(別リポジトリ `markharness-viewer`)は、作業ツリーの現在の状態だけを、StrictDoc要求の木と、要求に紐づかないFeatureの木の2本で示し、追加・編集の操作を、すべてのタイルに並べていた。一方で、要求のレーンと、ケースのレーンを、横に並べる形は、要求とケースを見比べるのに向いていた。

## 決定

- 画面は、上部の文脈バー(読むコミットと更新)、左の要求の一覧、右の詳細ペインで構成する。視点の切り替えは、第1版では行わない。
- 一覧は、**1行が1つの要求**とする。StrictDocの文書と節は、元の文書と見比べられるように、見出しとして残す。
- 要求の行に、次の項目を、左から順に出す。
  - 親の要求(StrictDocの `Parent` が指している要求。親のない要求は、「—」)
  - 要求の題名と本文。親になっている要求には、「子の要求: n件」を添える
  - ケース数(本体の `coverage` が、その要求に紐づけて返したケースの数)
  - 紐づくケースの題名(並べて)
- テストが紐づいているかどうかは、**ケース数で読む**。専用の列は設けない。StrictDocにだけある要求(markharnessに対応する要求がない)も、ケース数は0件と示す。「StrictDocにだけある」ことと「ケースが0件」であることは、厳密には別の事実だが、第1版で、確認対象を見つける手がかりとしては、ケース数0件で足りる。ケースがない理由(本体が報告する `gaps`)は、行には出さず、詳細ペインにだけ出す。
- StrictDocの親子は、**関係そのもの**を事実として示す。親の要求と、その要求を `Parent` に指している要求(子の要求)を、押すと、その要求へ移れるようにする。「上位・下位」の区別や、入れ子への組み替え、親子の上での集計は、行わない。一覧の並びは、StrictDocの文書と節の順のままとする。
- 判定として扱うのは、テストが紐づいているか、いないかだけとする(0009)。事実を表示するだけで、強調、色分け、並べ替え、折り畳み、親子の集計は行わない。
- Feature・Behaviorは、行に出さない。詳細ペインに、紐づき順(親 → 子)で出す。
- 詳細ペインは、**データの紐づき順(親 → 子)**に並べ、出所の札(StrictDoc、markharness)を付ける。
  - ケースを選んだとき: 要求 → Feature → Behavior → ケース(選んだ要素。説明、手順と期待結果、検証方法)の順。親は、題名だけの小さなカードにする。
  - 要求を選んだとき: 親の要求、選んだ要求(要求内容、markharnessの情報)、子の要求(縦に並べる)、紐づくケースの順。
- 検証方法(方法と参照先)は宣言であり、**検証結果は表示していない**ことを、画面に明記する。
- 操作(将来の編集を含む)は、選んだ要素の詳細ペインに置く。
- 要素の同一性は、`*_uid` で判断する。

## 代替案

- **視点ごとに、別の画面にする**: 部品が3組になり、後から編集を加えるときの置き場も、3か所になる。第1版では、視点の切り替え自体を行わない。
- **先行モックアップのように、木を2本にする**: Featureの位置が、紐づきの有無で移り、同じ要素を探しにくい。
- **Feature → Behavior → Scenarioの段を下げた木にする**: 要求の行に判断の材料が出ず、人間の注意が、階層に使われる。
- **要求 → ケースの2段の木にする**: 段は減るが、要求の行が、数字1つになり、要求とケースを左右で読み比べられない。
- **StrictDocの親子で、一覧を入れ子に組み替える**: 人間には自然に見えるが、StrictDocの文書・節の並びと、見出しが失われ、StrictDocにない意味(上位・下位、配下)を、GUIが足すことになる。関係そのものを示し、押して移れるようにすれば、一覧を組み替えずに、たどれる。
- **「StrictDocにだけある要求」を、別に示す**: StrictDocとmarkharnessを突き合わせて、GUIが新しい事実を作ることになる(0009の原則に照らして、第1版では行わない)。
- **親の有無(あり、なし)だけを示す**: 親が誰かが分からず、親から子へ、たどれない。
- **先行モックアップの、要求とケースの対応表(C案)**: 先行モックアップは、「検証方法・実装状態を、セルを選ばずに判別できない」ことを理由に、主表示に採用しなかった。この決定では、ケースを題名だけにし、状態は、詳細ペインに置く。ケースの量が増えたときの扱い(折り畳み)は、後で決める。

## 影響

- 要求とケースの対応は、本体の出力の紐づき(Feature単位とScenario単位)から作る。親を `uid` で指す出力が要る。
- 詳細ペインに、説明文や手順を出すには、本体の読み取り出力に、その項目が要る。
- 要求の行に、本文を出すには、StrictDocの要求の本文が要る(`traceability` は、external Requirementの本文を持たない)。StrictDocの要求の本文と、親子の扱いは、別に決める。
- `coverage` は、コミット済みの内容だけを読む。画面は、1つのコミットに固定して、`traceability` と `coverage` を、同じコミットで読む。
