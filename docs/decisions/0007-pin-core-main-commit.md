# 0007: 開発中は、本体のmainの固定コミットに対して開発し、結合テストで検証する

## ステータス

Accepted(2026-10-04決定)。[0006](0006-pin-core-commit-during-development.md) を置き換える。GUIが、編集まで含めて、正式版になり、`markharness gui` が本体の `main` にマージされたとき、本体のリリースへの固定に移る(出口の条件)。

## 背景

`markharness gui`(本体の起動の窓口)は、GUIが正式版になるまで、本体の `main` にマージされない。本体の保守者の方針である。`main` にあるものは、その時点に巻き戻したときに、十全に動くこと。本体のリリースが、GUIの出来に巻き込まれないこと。

0006は、この方針のもとで、本体のGUI開発用ブランチ(PR #94)の先頭に固定した。しかし、実際に確かめると、本体の `main` には、`traceability`、`coverage`、`impact` が、すでに入っている。PR #94のブランチと `main` の違いは、`markharness gui` の起動処理と、その文書だけである。GUIの画面の開発は、起動処理を経由しない(`--dir` と `MARKHARNESS_BIN` で動く)。ブランチに固定する理由は、無かった。

GUIが本体に求める読み取り出力の変更も、`gui` とは無関係な、通常の本体のPRとして、`main` に入れられる。保守者の方針の対象は、`markharness gui` だけである。

## 決定

- GUIが対応する本体は、`.github/markharness-rev` に記録した、本体の `main` のコミット1つだけである。古いリリースへの互換は、考えない。
- CIは、そのコミットから `markharness` をビルドして、実物の `markharness` を呼ぶ結合テストを実行する。手元でも、同じ手順(PROJECT.mdの標準コマンド)でビルドする。
- 固定の更新は、GUI側のPRで、手動で行う。固定の更新と、結合テストの通過を、同じPRで行う。
- GUIが本体に求める読み取り出力の変更は、本体のissueにして、本体の `main` に入れてもらう。入ったら、固定を更新するPRで、GUI側の対応を行う。
- `markharness gui` からの起動の確認は、固定した本体では行えない。本体のPR #94のブランチをビルドして、手動で確かめる。リリースのパイプラインを作るときに、自動の確認を整える。
- **出口の条件**: GUIが、編集まで含めて、正式版になり、`markharness gui` が本体の `main` にマージされたとき、本体のリリースへの固定に移る(本体のADR 0038 決定4・5)。そのとき、この決定を `Superseded` にする。

## 代替案

- **本体のGUI開発用ブランチ(PR #94)の先頭に固定する(0006)**: GUIの開発が使わない起動処理のために、ブランチの強制pushで固定したコミットを失うおそれと、PRのスタックのマージ順への依存を負う。
- **公開済みの `v0.6.1` に固定する**: `traceability` を持たないため、対応できない。
- **本体が、プレリリースを出すまで待つ**: 本体のリリースが、GUIの開発の律速になる。
- **本体の `markharness gui` を、いま `main` にマージする**: 本体の保守者の方針に反する。未完成のGUIの窓口が、本体のリリースに載る。
- **本体の `main` の先頭に、常に追従する**: ビルドが、再現できない。どの本体に対して通ったのか、分からなくなる。
- **本体の `main` の先頭に対して、結合テストを定期的に動かす(カナリア)**: 本体の変更が、GUIを壊したことを、早く知らせる。いまは、過剰である。必要になってから、加える。

## 影響

- CIで、本体のビルドが加わる(手元で約50秒。キャッシュを使う)。
- 本体の `main` のコミットは、履歴に残るので、取得できなくなるおそれが、実質、無い。
- 本体の隙間を、GUIから見つけたら、本体への依頼(issue)にする。
