# 0008: 表示は、要求を根にした1本の木と詳細ペインを、3つの視点で共有する

## ステータス

Accepted(2026-10-04決定)。木の見た目、StrictDocとの連携、詳細ペインに出す内容は、別に決める。

## 背景

本体の読み取り出力(`traceability`、`coverage`、`impact`)は、どれも、要求を根にした「要求 → Feature → ケース」の構造を持つ。関係、Release Coverage、Change Impactを、別々の画面にすると、同じ構造の木を、画面ごとに作ることになる。

先行モックアップ(別リポジトリ `markharness-viewer`)は、作業ツリーの現在の状態だけを、StrictDoc要求の木と、要求に紐づかないFeatureの木の2本で示し、追加・編集の操作を、すべてのタイルに並べていた。木の位置が、紐づきの有無で変わるため探しにくく、操作が、レビューの視線を妨げる。

## 決定

- 画面は、上部の文脈バー(読むコミット、リリース、比べる範囲)、左の要求を根にした木、右の詳細ペインで構成する。
- 「関係」「Release Coverage」「Change Impact」は、別の画面ではなく、同じ木と詳細ペインを共有する**視点**とする。視点を切り替えると、先頭の要約と「注意が要るもの」、木の行に重ねる情報が変わる。
- 木は、要求を根に、1本とする。複数の要求に紐づくFeatureは、それぞれの下に出す。要求に紐づかないものは、消さずに「要求に紐づかない」にまとめる。
- 木の行は、読み取り専用とする。操作(将来の編集を含む)は、選んだ要素の詳細ペインに置く。
- 要素の同一性は、`*_uid` で判断する。
- 件数や状態の判定は、本体の出力に従い、GUIは、計算し直さない。件数や関係の有無から、充足や合否を、断定しない。

## 代替案

- **視点ごとに、別の画面にする**: 部品が3組になり、後から編集を加えるときの置き場も、3か所になる。視点ごとに、注目する順序が違う点は、先頭の要約と並べ替えで吸収できる。
- **先行モックアップのように、木を2本にする**: Featureの位置が、紐づきの有無で移り、同じ要素を探しにくい。

## 影響

- `coverage` と `impact` は、コミット済みの内容だけを読む。木は、文脈バーで選んだ1つのコミットに固定して、3つの出力を、すべて、同じコミットで読む。作業ツリーの未コミットの内容を、どの視点で見せるかは、編集を設計するときに決める。
- 木の階層(Feature → Behavior → Scenario → TestCase)は、本体の出力の親子関係から作る。同じslugを複数のFeatureが持つ構成を扱うには、親を `uid` で指す出力が要る。
- 詳細ペインに、説明文や手順を出すには、本体の読み取り出力に、その項目が要る。
