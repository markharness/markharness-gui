# 0006: 開発中は、本体の `main` の固定コミットに対して開発し、結合テストで検証する

## ステータス

Accepted(2026-10-04決定)。GUIが正式版になり、`markharness gui` が本体にマージされたときに、本体のリリースへの固定へ移る(出口の条件)。

## 背景

`markharness gui`(本体の起動の窓口)は、GUIが正式版になるまで、本体にマージされない。そのため、このGUIは、本体の完全なリリースより前の状態で、まず、本体にとって有用でなければならない。いまの価値の中心は、次の2つである。

- 本体の読み取り出力の、最初の実利用者として、設計の隙間を早く見つける。
- 本体の読み取り出力の変化を、結合テストで検出する網になる。

公開済みの本体 `v0.6.1` は、`traceability` を持たない(`gui` も持たない)。本体の `main` は、`v0.6.1` から49コミット先に進んでいるが、バージョンの文字列は、同じ `0.6.1` のままで、ビルドを区別できない。本体の読み取り出力の `schema_version` は、0.xの間、`1` に凍結されているので、出力の形の変化は、版の確認では検出できない。

## 決定

- GUIが対応する本体は、`.github/markharness-rev` に記録した、本体の `main` のコミット1つだけである。古いリリースへの互換は、考えない。
- CIは、そのコミットから `markharness` をビルドして、実物の `markharness` を呼ぶ結合テストを実行する。手元でも、同じ手順(PROJECT.mdの標準コマンド)でビルドする。
- 固定の更新は、GUI側のPRで、手動で行う。固定の更新と、結合テストの通過を、同じPRで行う。
- **出口の条件**: GUIが正式版になり、`markharness gui` が本体にマージされたとき、本体のリリースへの固定に移る(本体のADR 0038 決定4・5)。そのとき、この決定を `Superseded` にする。

## 代替案

- **公開済みの `v0.6.1` に固定する**: `traceability` を持たないため、対応できない。
- **本体が、プレリリースを出すまで待つ**: 本体のリリースが、GUIの開発の律速になる。待つ間、結合テストを外すと、本体の出力の変化を検出する、唯一の網が無くなる。
- **本体の `main` の先頭に、常に追従する**: ビルドが、再現できない。どの本体に対して通ったのか、分からなくなる。
- **本体の `main` の先頭に対して、結合テストを定期的に動かす(カナリア)**: 本体の変更が、GUIを壊したことを、早く知らせる。いまは、本体との連携の手順が、まだ無いため、過剰である。必要になってから、加える。

## 影響

- CIで、本体のビルドが加わる(手元で約50秒。キャッシュを使う)。
- 固定したコミットは、`markharness gui` を含まない。ランチャーからの起動の確認は、`gui` を含む本体のブランチのビルドで行う。
- 本体の隙間を、GUIから見つけたら、本体への依頼(issue)にする。本体が対応したら、固定を更新するPRで、GUI側の対応を行う。
