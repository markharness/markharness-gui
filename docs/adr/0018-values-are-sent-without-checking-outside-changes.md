# 0018: 開いているフォームの値は、外からの変更を確かめずに送る

## ステータス

Accepted(2026-10-09決定)。

## 背景

編集と作成のフォームは、開いた時点の値を持ち、保存のときに、その値を送る。コアの `reconcile` には、前の版との照合の指定がない。画面は、ファイルの変更を監視しない。

そのため、同じPCで画面とCLIを同時に使うと、次の順で、CLIの変更が、画面の保存で上書きされうる。

1. 画面でフォームを開く。
2. CLIで、同じ要素を変更する。
3. 画面で保存する。

手順・期待結果や共通手順のように、全体を置き換える項目では、上書きされる量が大きい。要求の作成で引き取るFeatureの候補も、フォームを開いた時点のデータから作るため、同じ状況で、外から別の要求に紐づけられたFeatureが、候補に残りうる。

## 決定

- 保存の前に、外からの変更を確かめる仕組みは、持たない。この上書きを、既知の許容リスクとする。画面とCLIを同時に使う運用が、実際にあるとわかった時点で、その運用に合わせて、確かめる仕組みを設計する。
- CLIの変更は、画面上部の「再読み込み」で反映する。再読み込みは、一覧・カード・要求の説明・検証方法・コミット済みの内容の検証に加えて、選んでいるケースの説明と手順・期待結果も、読み直す。
- フォームの値は、フォームを開くたびに、コアから読み直す。

## 代替案

- **保存の直前に読み直し、フォームを開いた時点と違えば、保存を止めて知らせる**: 採用しなかった。外からの変更を確かめずに、フォームの値を送る。
- **ファイルの変更を監視して、画面を自動で更新する**: 採用しなかった。利用者が「再読み込み」を押す。

## 影響

- 画面とCLIを同時に使う利用者は、CLIで操作したあとに、「再読み込み」を押し、フォームを開き直してから、画面で保存する。
- レビューでは、この上書きは、記録済みの許容リスクとして扱う。この決定の条件を広げる変更(たとえば、画面の外からの変更を、保存の前に確かめないまま、より大きな単位で送るようにすること)は、指摘の対象とする。
