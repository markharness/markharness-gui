# 0011: 一覧は、作業ツリーの `traceability` だけで作り、`coverage` は裏で読む

## ステータス

Accepted(2026-10-06決定)。[0008](0008-requirement-rows-and-detail-pane.md) の「画面は、1つのコミットに固定して、`traceability` と `coverage` を、同じコミットで読む」を置き換える。

## 背景

第1版の目的は、人間が、現在の作業について、テストケースの紐づきを、一目で分かるようにすることである。「現在の作業」は、未コミットの編集を含む作業ツリーである。

0008は、`coverage` がコミット済みの内容しか読めないため、`traceability` にも `--at` を付けて、同じコミットで読むと決めた。しかし、Windowsで測ると、この決定が、画面が出るまでの時間を伸ばしていた。

- `coverage` は、`git` をファイルごとに起動していて、約13.6秒かかった(コミット1件、要求18件のプロジェクト)。
- `traceability --at` は、約2.4秒かかった(`--at` なしは約0.09秒)。
- 2つを直列に読むため、画面が出るまで、約16秒かかった。

また、`coverage` を一覧に使うと、編集してコミットするまで、一覧が変わらない。「現在の作業」を見せるという目的に合わない。

本体は、この問題を受けて、次の3つを直した。

- `coverage` が起動する `git` の数を、ファイルの数と要求の数に依らなくした(同じプロジェクトで、約1.0秒になった)。
- `traceability` の `requirements[]` に、紐づくケースの一覧 `case_uids` を加えた。規則は `coverage` と同じ関数で、2つの出力は食い違わない。
- `traceability` を、作業ツリー専用にした。`--at` と、出力の `at` を、廃止した。

## 決定

- 画面の一覧(要求の行のケース数と、ケースの題名)は、`traceability`(作業ツリー)の `requirements[].case_uids` だけで作る。
- 第1版は、常に作業ツリーを見せる。読むコミットを、利用者は選べない。
- `coverage`(コミット済みの `HEAD`)は、一覧が出たあとに、裏で読む。検証手段、参照先の状態、`gaps` は、詳細ペインに出す。
- 画面は、一覧が作業ツリーであること、`coverage` 由来の内容がコミット済みの内容であること(そのコミット)を、明記する。
- `coverage` の読み込み中は、詳細ペインに「読み込み中…」を、読めなかったときは「読めませんでした」と、理由を通知(トースト)で示す。一覧は、どちらでも妨げない。
- 要求とケースの紐づきの規則は、本体が持つ。GUIは、`relations` から、紐づきを計算しない。

## 代替案

- **一覧にも `coverage` を使う(0008のまま)**: 編集が、コミットするまで、一覧に出ない。また、`traceability` を `--at` で読む必要があるが、本体が `--at` を廃止した。
- **`relations` から、GUIが紐づきを計算する**: ScenarioがRequirementを指すと、Featureの指定を上書きする規則がある。単純に足すと、`coverage` と食い違う(実測で、18要求のうち2件)。規則が変わるたびに、GUIの計算がずれる。
- **コミットを選べるようにする**: 第1版の範囲に含めない。必要になったときに、`coverage --at` と、本体の出力に合わせて決める。
- **`coverage` を、詳細ペインを開くたびに読む**: 開くたびに待つことになる。一覧が出たあとに一度だけ読めば、詳細を開くころには揃う。

## 影響

- 一覧が作業ツリー、詳細の一部がコミット済みの内容になり、2つが食い違って見えることがある(未コミットの編集があるとき)。画面に、それぞれの出所を明記して、利用者が区別できるようにする。
- コミット済みを基準に、作業ツリーとの差を示すことは、将来の課題である。
- 本体の `traceability` が `--at` を持たないため、固定する本体のコミットは、本体のPR #116 以降でなければならない([0007](0007-pin-core-main-commit.md))。
