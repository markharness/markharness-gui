# レビューの方針

この文書は、このリポジトリにおける、コードレビューの判断の正です。レビュアーは、コード、ブランチ、差分、プルリクエスト、またはチェックリストや仕様に対する実装をレビューするときに、これを適用しなければなりません。

> この方針は、markharness本体のレビューの方針を、GUI向けに翻案したものです。脅威モデルと「リポジトリの既定」は、GUIの性質とmarkharness本体のADR 0038の決定に基づいて書き換えています。技術スタックと実行形態の確定後に、見直してください。

## プロジェクトの脅威モデル

`markharness-gui` は、単一の開発者や利用者が、自分の作業コピーに対して実行する、ローカルのGUIです。特定の機能について、承認済みのADRや設計文書が別に定めていない限り、基本の脅威モデルは次のとおりです。

- OS、ファイルシステム、同じユーザーで動く他のプロセス、およびGUIが呼び出す `markharness` と `strictdoc` の実行ファイルは、信頼します。GUI自身と同じ権限を持つプロセス(GUIが書き込める場所のどこにでも書き込めるプロセス)は、このプロジェクトが防御する敵対者では**ありません**。そのプロセスは、どのような競合状態よりも、単純な方法で、同等以上の損害を与えられるからです。
- 作業中のプロジェクトのディレクトリは、GUIの実行中に、ネットワークファイルシステムなどを含め、信頼できない相手と共有されません。個別の指摘の証拠が、実際にはそのように使われていることを示している場合を除きます。
- 悪意のある**入力**は、対象です。細工されたリポジトリ、細工されたKnowledgeのYAMLファイル、細工されたStrictDocの文書、細工された `markharness` や `strictdoc` の出力が、これにあたります。これらの文字列が画面に表示されるとき(ラベルや本文を、実行可能な内容として解釈しないこと)と、ファイルのパスやコマンドの引数として使われるとき(コマンドへの注入が起きないこと)が、主な対象です。攻撃者が選んだタイミングで、ファイルシステムの操作に割り込む、悪意のある**並行プロセス**は、既定では対象外です。
- GUIが、ローカルで接続を待ち受ける実行形態(たとえば、ローカルサーバーとブラウザ)を採る場合、同じマシン上の他のプロセスや、ブラウザで開かれた別のWebページからの到達は、実行形態を決める時点で、脅威として評価します。評価の結果は、ADRに記録し、この節を更新します。

到達可能性を評価するときは、この脅威モデルを適用します。影響に至る唯一の経路が、プロジェクトのディレクトリに対して、すでに敵対的で、並行で、任意のタイミングの書き込み権限を持つ行為者を必要とする指摘は、その行為者が、「すでにこのプロジェクトのファイルに書き込める」ことよりも、意味のある程度に少ない能力で、その立場に到達できない限り、既定では `Must fix` ではなく、`Accepted risk` か `No finding` とします。「適切なタイミングなら、理論上は可能」というだけで、到達可能性は十分とはみなしません。

これは、通常の使用、操作ミス、または、同じ操作者によるGUIの通常の(敵対的でない)並行利用で到達できる `Must fix` の項目を、緩和するものではありません。それらは、この節にかかわらず、対象のままです。

## YAGNI

YAGNI(You Aren't Gonna Need It)を、実装とレビューの両方に適用します。現在の具体的な要求が必要とするものだけを、作り、求めます。

- まだ存在しない必要性のために、汎用化、設定可能性、抽象化の層、拡張ポイントを、提案したり求めたりしません。「後で必要になるかもしれない」は、それだけでは、指摘や修正の根拠になりません。
- [プロジェクトの脅威モデル](#プロジェクトの脅威モデル)が対象外とする能力やシナリオに対するハードニングを、提案しません。技術的には塞げるとしても、塞げる穴が、自動的に塞ぐ価値のあるものになるわけではありません。ほかの指摘と同じように、修正のコストと変更のリスクで比較し、要求する行為者の能力がすでに対象外である場合は、`Accepted risk` か `No finding` を既定とします。
- 指摘に対する提案する修正が、新しい抽象化、依存、設定の面を加える場合は、報告された条件だけを解決する版の修正を優先します。より広い汎用化は、多くとも `Follow-up` として記し、必須の修正の一部にはしません。

## レビューの軸

変更を、次の2つの軸について、それぞれ独立にレビューします。指摘は、対応する見出しの下に報告し、一方の軸が、もう一方を覆い隠さないようにします。

### 標準(Standards)

変更が、リポジトリの指示、`CONTRIBUTING.md`、承認済みのADR、設計文書の不変条件、文書化されたモジュールのインターフェース、確立した安全上の制約に従っているかを判断します。文書化されたプロジェクトの決定は、一般的なコードの匂いに関する好みに優先します。

コメントとドキュメントの配置には、リポジトリの情報配置の方針を適用します。コードは現在のWhat/Howを持ち、コメントは局所的なWhy・不変条件・コードから明らかでない制約を持ち、ADRは設計の選択と代替案を持ち、Git履歴は実装の経緯を持ちます。コメントが実装を言い換えているだけの場合、正しさに関わる局所的な制約が文書化されていない場合、設計の理由や歴史的な経緯が誤った媒体に重複している場合は、指摘として報告します。コード・型・テスト・命名からすでに明らかな情報に、コメントを求めてはいけません。

### 仕様(Spec)

変更が、依頼されたチェックリスト、issue、仕様を、完全かつ正しく実装しているかを判断します。欠けている、または部分的な要件、誤った振る舞い、依頼の範囲外の重大な振る舞いを、報告します。

## 変更の規模に合わせたレビューの深さ

すべての変更に、下の判断軸の全工程が必要なわけではありません。規模とリスクに合わせて、労力を調整します。

- **小さい変更**(数行で、触れる不変条件がなく、セキュリティに関わる経路でもない): 標準と仕様を直接確認します。何かおかしい点が見える場合を除き、判断軸の全工程は省きます。
- **通常の変更**: 指摘の候補ごとに、[判定の決め方](#判定の決め方)を適用します。
- **セキュリティ、markharnessとの契約、キャッシュの鮮度に関わる変更**(markharnessのJSONの読み取りと版の確認、編集による書き込み、StrictDocのエクスポートのキャッシュ、文書化された不変条件に触れるもの): 差分の大きさにかかわらず、判断軸の全工程を、常に実行します。

## 判定の決め方

指摘の候補ごとに、次の問いを順に考えます。証拠を示し、理由のある判断をします。数値のスコアに還元してはいけません。

| 問い | どの判断に効くか |
| --- | --- |
| 明示された仕様、不変条件、承認済みのADR、文書化されたインターフェースに違反しているか | `Must fix` か、それ以外か |
| 最悪の場合の影響は何か。影響を受けた状態は、自動で、手動で、または全く回復できないのか | 重大度 |
| 通常の使用や操作ミスで到達できるか。それとも、敵対的、または任意のタイミングのアクセスでだけ到達できるのか([脅威モデル](#プロジェクトの脅威モデル)) | `Must fix` か、`Accepted risk` か |
| 修正は局所的でテストできるか。それとも、大きな新しい複雑さ(新しい依存、広範なリファクタリング)が必要で、修正自体が、塞ごうとする条件よりも大きなリスクを持ち込みかねないか | `Should fix` か、`Accepted risk` か |
| この変更が、その条件を持ち込んだ、悪化させた、または新たに露出させたのか。それとも、すでに存在し、手が加わっていないのか | `Should fix` か、`Follow-up` か |

既定は**承認**です。`Should fix` 水準の指摘が1つあるだけでは、それ単体でマージを止めません。マージを止めるのは、`Must fix` の項目に限ります。仕様や不変条件の違反、データの破損、プロジェクトのルートの外への書き込み、回復できない状態、または、通常の並行利用で文書化された不変条件が破られる、という信頼できるリスクです。

## 判定

報告するすべての項目に、判定を、ちょうど1つ付けます。

### Must fix

マージを止めます。仕様や不変条件の違反、およびデータの破損(GUIの編集による、Knowledgeの破損や誤った関連付けを含む)、プロジェクトのルートの外への書き込み、回復できない状態、あるいは、通常の並行操作が、文書化された不変条件を破ることが、信頼できるリスクです。

### Should fix

修正するのが現実的で、釣り合いが取れているが、それ単体ではマージを止めません。必要な、具体的な修正と検証を示します。

### Accepted risk

条件は実在するが、その可能性、必要な能力、影響、または修正のコストから、受け入れるのが妥当と判断できる場合です。受け入れるには、次を含む、永続的な記録が必要です。

- 条件と、起こりうる影響
- 必要な能力と、到達可能性
- 既存の緩和策
- 却下した緩和策と、そのコストとリスク
- 受け入れる理由
- 見直しの明示的なきっかけ

機能固有の許容リスクは、関連する承認済みのADRや設計文書に記録します。レビュアーは、文書化された許容リスクを、レビュー対象の変更が、その到達可能性や影響を広げる、許容の条件に違反する、緩和策を無効にする、または、大幅に安く安全な緩和策が利用できるようになる場合を除き、再び報告してはいけません。

### Follow-up

信頼できるが、レビューの範囲の外にあり、この変更によって持ち込まれず、悪化せず、新たに露出もしていない場合です。ブロックする指摘とは別に報告し、どこで追跡するかを示します。

### No finding

報告しないものすべての既定です。文体の好み、ツールが強制する書式、裏づけのない推測、該当する許容リスクの記録がすでに扱っている振る舞いを、報告してはいけません。コメントや設計文書が、実装が提供するよりも強い保証を約束している場合は、その食い違いは、もとのリスクが別の形では受け入れられうるときでも、指摘として残ります。実装を強めるか、文書化した保証を狭めるかの、どちらかです。

## リポジトリの既定

より具体的な承認済みのADRや設計文書が別に定めていない限り、次の既定を適用します。

- GUIが、`.markharness/` 配下の内部ファイルを直接読み書きすること(StrictDocのエクスポートを除く)、または、Knowledgeのファイルを `knowledge reconcile` を通さずに書き換えることは、`Must fix` です(markharness本体のADR 0038 決定2・10)。
- 古い内容を、利用者が抜け出す手段のないまま見せ続けることは、`Must fix` です(同、決定7)。
- 対応しない版、意味を解釈する値の集合の未知の値、必要な項目の欠落を、止めずに、黙って除外して表示することは、`Must fix` です(同、決定5)。
- GUIの編集による、Knowledgeの破損や、誤った関連付けは、`Must fix` です。
- 永続的なファイルシステムやコマンド実行の失敗の原因を失い、通常の、または再試行できる結果に変えてしまうことは、少なくとも `Should fix` で、安全でない継続を許しうる場合は `Must fix` になります。
- 狭い、プラットフォーム固有の残余リスクは、それを塞ぐのに不安定で高リスクなネイティブ呼び出しや大きな依存が必要で、行為者がすでに破壊的な書き込み権限を必要とし、残る保証が正確に文書化されている場合は、受け入れてかまいません。
- すでに存在する問題は、レビュー対象の変更がそれを悪化させる、新たに到達可能にする、または、違反されている振る舞いに、正しさを依存させるのでない限り、`Follow-up` です。
- 競合を塞ぐために、低水準のプラットフォーム固有の仕組み(ネイティブの呼び出し、新しい低水準の依存)を、追加したり広げたりすることは、変更のリスクのシグナルであり、無条件に良い行為ではありません。その条件を引き起こせる唯一の行為者が、[脅威モデル](#プロジェクトの脅威モデル)で述べたアクセスをすでに必要とする場合は、その仕組みの追加や拡大よりも、`Accepted risk` を優先します。そのような仕組みによるハードニングは、通常の使用、操作ミス、または、「すでにこのプロジェクトに書き込める」よりも意味のある程度に少ないアクセスの行為者で、到達できる条件のために、とっておきます。

## レビューの手戻りを避ける

- この方針自体が変わる場合や、新しい要件(許容リスクの6つの要素など)が導入される場合は、既存の許容リスクの記録のすべてを、1回の通しで、これに照らして確認し、不足を、1つの指摘(または影響を受ける文書ごとに1つの指摘)にまとめて報告します。不足の要素ごとに指摘を分けることはしません。1つの方針への不適合を、連続する複数のレビューのラウンドに分散させてはいけません。
- 指摘の内容のすべてが、「この許容リスクの記録の文章が、必要な要素の1つを文字どおりに言い直していない」ことだけで、その根拠となるリスクの判断(条件、能力、到達可能性、緩和策、受け入れの理由)が、変わらず正しい場合は、その判断が実質的にすでに1回記録されている以上、`No finding` です。より厳しい見出しや箇条書きの構造に直すために、2回目のラウンドを求めてはいけません。
- 前のラウンドの指摘に対する修正である変更に、新しいレビューのラウンドを開く前に、前の指摘の証拠がもう当てはまらないことを確認します。修正が正しければ、その指摘についてのレビューは終わりです。本当に別の条件を述べるのでない限り、同じ証拠の場所を使って、隣り合う、より狭い指摘を開いてはいけません。

### 完全な1回の通しと、再レビューの規律

レビューは、著者に、現在の変更の完全で実行可能な全体像を、1回で渡すものであり、独立に見つけられる問題を、何回ものラウンドにわたって小出しにするものではありません。

- レビューの開始時に、差分によって変わる振る舞いを列挙し、それぞれを、標準と仕様の両方の軸で確認します。通常の失敗の経路と、明示された契約に重要なプラットフォームの振る舞いを含みます。この通しが終わる前の観察は、最終的なレビューの結果ではなく、途中のものとして扱います。
- レビューの結論を出す前に、全体の通しを終え、その通しで見つけたすべての指摘を、まとめて報告します。後のラウンドで、すでに確認済みで変更のない振る舞いを、近くの端の事例を追うためだけに、新しい指摘に変えてはいけません。
- 修正にも、実装と同じように、YAGNIを適用します。狭い修正が、現在のissueを満たし、適用される不変条件を保つ場合は、一般的な仕組みを求めずに、その修正を勧めます。著者が、それでもより広い契約を導入した場合は、新たに約束された振る舞いをレビューしますが、より広い契約を維持することは、求めません。
- issueの範囲に限った変更では、上のとおり標準と仕様をレビューしますが、ブロックする指摘は、その変更が持ち込んだ、悪化させた、または新たに露出させた違反に限ります。無関係な、すでに存在する問題は、多くとも `Follow-up` です。
- `Must fix` は、この方針が定める条件のために、とっておきます。移植性の端の事例や、珍しいファイルシステムのオブジェクトを、通常の使用で信頼できる形で到達でき、明示された要件や不変条件に違反しない限り、`Must fix` に格上げしてはいけません。すべての端の事例に対する一般的な解決を完成させるよりも、不要な保証を狭めることを優先します。

修正の変更を再レビューするときは、次の順にします。

1. まず、以前の指摘のそれぞれが、解消された、まだ残っている、または、実装や文書化した契約を狭めることで、意図的に対処されたのかを判断します。
2. 修正が新たに加えた、または変えた振る舞いのすべてを、同じ通しでレビューします。修正が、その条件を持ち込んだ、悪化させた、または新たに露出させた場合は、新しい指摘が適切です。
3. 新しい指摘が、前に完了したレビューで、変更がなく、確認できる状態にあった振る舞いに関するものである場合は、それをレビュアーの見落としと、明示的に記します。著者の最新の修正の結果として提示してはいけません。その振る舞いから、独立に見つけられる残りの問題は、同じラウンドにまとめます。
4. 最後に、明示的なマージの判定を述べます。`mergeable`(マージ可能)、`mergeable with non-blocking follow-up`(ブロックしない追跡事項つきでマージ可能)、`not mergeable`(マージ不可)のいずれかで、ブロックする指摘を明示します。ブロックする指摘が残っていない場合は、そのことを直接述べます。

## 指摘の形式

それぞれの指摘は、それ単体で完結し、次を含まなければなりません。

```text
- [判定][重大度] 短い題名
  - 根拠: ファイルと行、失敗するテスト、または再現できる振る舞い
  - 違反した契約: 仕様、不変条件、基準、またはインターフェース
  - 到達可能性と、必要な能力
  - 影響と、回復可能性
  - 提案する修正
  - 修正のコストとトレードオフ
  - 必要な検証
```

重大度(`Critical`、`High`、`Medium`、`Low`)は、影響と緊急度を表すために使い、判定は、何をすべきかを述べるために使います。この2つは、別の判断です。

ある軸に指摘がない場合は、そのことを明示します。レビューは、軸ごとの指摘の件数と、各軸の中で最も高い重大度の判定を述べて、終えます。レビューの作業は、変更されたすべての振る舞いと、適用されるすべての要件を、両方の軸で検討し終えたときに、完了します。
